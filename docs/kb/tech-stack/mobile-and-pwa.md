# Mobile and PWA

How Optimus is built mobile-first and delivered as an installable Progressive Web App, with an Android shell in MVP and an iOS shell deferred.

## Current State

Pre-implementation. The mobile-first stance is a project principle; the PWA tooling and Capacitor-shell strategy are locked.

## Mobile-first as a principle

The consumer flow, the contractor dashboard, and the borrower experience are all primarily-mobile. The driver is the in-home sale: the contractor opens the app on their phone, often hands the phone to the homeowner, or sends a link the homeowner opens on their own phone (see [application-flow.md](../application-flow.md), section "Two origination modes"). Mobile is the default surface, not a responsive afterthought.

Concretely, every page and component is built to function at **360px width minimum**, with progressive enhancement upward. Touch targets meet accessibility minimums (WCAG 2.1 AA — 44×44 px effective). Forms are designed for thumb reach. Modals avoid blocking the keyboard on small screens. Navigation patterns assume one-handed phone use first, then desktop second.

This is a stronger commitment than "mobile-friendly." Mobile-friendly is "the desktop layout doesn't break on small screens." Mobile-first is "the small-screen layout *is* the design, and desktop adds breathing room."

## PWA: vite-plugin-pwa, InjectManifest mode

The frontend (`frontend/`) uses Vite, and `vite-plugin-pwa` integrates the PWA pieces:

- **Web app manifest** at `frontend/public/manifest.webmanifest`: app name, short name, icons (multiple resolutions), `theme_color`, `background_color`, `display: standalone`, `scope`, `start_url`. This is what makes the app installable from a browser.
- **Service worker** at `frontend/src/sw.ts`. Mode is **InjectManifest** — we own the service worker source; the plugin only injects the precache manifest at build time. This gives full control over caching strategies, offline behavior, and update handling, instead of accepting `generateSW`'s defaults.
- **Caching strategy** is conservative for MVP: precache the static asset bundle, network-first for API calls, runtime-cache for fonts. Aggressive offline support (offline-capable forms, queued submissions) is deferred until there's a demand.
- **Update flow**: when a new service worker is detected, prompt the user to refresh; never silently swap mid-flow because borrower applications can be in flight.

## Android: pure PWA + optional Bubblewrap TWA

Two paths to "an Android app experience," both MVP-acceptable:

1. **Pure PWA install via Chrome.** The user's browser shows an install prompt (or they choose "Add to Home Screen"). Chrome on Android creates a WebAPK — a near-native experience: own icon, own task in the recents view, full-screen with no browser chrome. No build step, no Play Store, no separate app artifact. This is the default path.
2. **Bubblewrap-generated TWA (Trusted Web Activity).** A native Android shell that hosts the PWA via Chrome Custom Tabs — the user's installed Chrome renders the PWA inside what looks like an Android app. Generated by Google's `@bubblewrap/cli` from a `twa-manifest.json` config, packaged as an `.aab`, submitted to the Play Store. The benefit is Play Store discoverability and the "real app" perception. The cost is one extra build pipeline plus a Play Console account ($25 one-time fee).

**Why Bubblewrap rather than Capacitor for Android:** Bubblewrap is a much lighter wrapper for "PWA in the Play Store." It leverages the user's Chrome engine via TWA, so there's no app-bundled WebView and no native-plugin layer to maintain. The Android-side code is essentially a launcher activity plus `twa-manifest.json`. Capacitor would add a separately-versioned WebView, a plugin runtime, and more native build complexity — overkill when we just want the same PWA installable from the Play Store.

Both paths point at the same web frontend. We can ship pure-PWA first and add the Bubblewrap TWA later for Play Store presence without rebuilding the web app.

## iOS: deferred from MVP

A native iOS shell is **not in MVP**. iPhone users still access the platform via Safari and get a functional PWA — they can "Add to Home Screen" too, though Safari's PWA support has historically lagged Chrome's (e.g., Safari doesn't run service workers across all PWA contexts the same way, and offline behavior differs).

When iOS does land post-MVP, the right tool is **Capacitor + WKWebView**. There is no iOS equivalent of Android's TWA: Apple doesn't permit alternative browser engines and there's no Chrome-Custom-Tabs analog. Capacitor wraps WKWebView and supplies the native plugins (`@capacitor/push-notifications`, `@capacitor/browser`, `@capacitor/app`, etc.) the iOS shell needs.

Why deferred:

- **Apple Developer Program** is $99/year and requires identity verification.
- **App Store review** adds a non-deterministic time cost on every release.
- **Capacitor iOS edge cases** are real: push notifications, deep linking, IDV camera permissions, file uploads, and Safari-specific quirks each need work that doesn't apply to Android.
- The MVP target is end of summer 2026; iOS native packaging is the kind of scope creep that pushes timelines.

The deferral is a "we know how to add it later" note, not a "we're abandoning iPhone users." iPhone users are first-class citizens of the web PWA on Day 1.

## What this means for application code

- Default styles and layouts assume small screens; `md:` and `lg:` breakpoints add desktop polish.
- Tap targets, font sizes, and spacing are tuned for finger interaction.
- Long forms split into steps when they don't fit comfortably on one phone screen — matches the application-flow's two-part split.
- File-upload affordances (e.g., voided cheque image during set-up-payments) use the device's native picker via `<input type="file" accept="image/*" capture="environment">` so phone users can take a photo directly.
- The PWA's start URL drops the user into a sensible landing page (different for borrower one-time-URL recipients vs. logged-in platform users).

## Key Decisions & Rationale

### Mobile-first, not mobile-friendly

**Why:** The product's primary use case is in-home selling and homeowner self-serve completion on a phone. Designing for desktop and shrinking down produces frustrating phone UX; designing for phone and growing up produces good UX everywhere.

**How to apply:** New features are designed and reviewed at phone-screen width first. If a desktop-only layout makes sense, it's an addition, not the baseline.

### vite-plugin-pwa in InjectManifest mode, not GenerateSW

**Why:** Service worker behavior touches user-visible flows (offline, updates, caching). Owning the source means we can debug it, log it, and version it like any other app code.

**How to apply:** Add to the service worker only when there's a clear win. Don't accept "the plugin set up something that mostly works."

### Pure PWA first, Bubblewrap TWA optional for Android

**Why:** Play Store presence is nice but not the primary distribution channel — contractors share links, not app store URLs. Adding the TWA shell when it's needed (or never, if the pure PWA suffices) keeps MVP scope smaller. Bubblewrap is also a lighter wrapper than Capacitor for the Android case — no app-bundled WebView, no native-plugin maintenance.

**How to apply:** Don't add Bubblewrap (or any Android native shell) unless there's a concrete reason (Play Store listing demand, etc.).

### Different shell tools per platform: Bubblewrap for Android, Capacitor for iOS

**Why:** Each platform has its own best-fit pattern. On Android, Bubblewrap/TWA leverages the user's installed Chrome — lighter, no extra WebView to ship or maintain. On iOS, Apple doesn't permit alternative browser engines and there's no TWA equivalent, so Capacitor + WKWebView is the standard answer. Trying to use one tool for both compromises one of them.

**How to apply:** When discussing "the native shell," be specific about platform — they're different stacks. Don't reach for Capacitor on Android "for consistency."

### iOS native deferred to post-MVP

**Why:** Adds significant non-product work (Apple Developer Program, review cycles, iOS-specific Capacitor edge cases) without changing what the app actually does for iPhone users on the web.

**How to apply:** Don't write iOS-specific code or iOS-only behaviors in MVP. The web frontend is the single deliverable for iPhone users.

## Known Limitations

- Safari PWA behavior on iOS will require explicit testing during MVP. Some features (push, background sync, certain camera/file APIs) may be limited or unavailable. Document workarounds; don't try to make the experience identical to Android.
- Service-worker update flow during a long-running application (e.g., borrower mid-flow when a deploy ships) needs care — the rule is "don't disrupt an in-flight session." The implementation plan should cover the exact strategy.
- The Bubblewrap TWA shell, if/when added for Android, is one more thing to build and sign per release. Plan the build pipeline only when the shell becomes scope.
- The Capacitor iOS shell, when iOS lands post-MVP, is a separate build with its own dependencies (Xcode, Apple signing certificates, App Store Connect). Don't bundle it into the same pipeline assumptions as the Android shell.

## Deferred / Future

- iOS native shell (Capacitor + WKWebView) — adds Apple Developer Program, App Store review, iOS-specific Capacitor edge cases.
- Bubblewrap TWA Android shell — pure PWA install is the default; the TWA shell is optional and can land later if Play Store presence is wanted.
- Aggressive offline support (offline-capable forms, queued submissions, sync). Conservative caching is fine for MVP.
- Push notifications — useful for borrower funding-authorization prompts and contractor approval-condition alerts; Android-only initially if added.
- Native-feature integrations beyond camera (biometric unlock, secure storage, app shortcuts) — out of scope until needed.
